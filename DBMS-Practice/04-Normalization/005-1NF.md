# 1NF (First Normal Form)

## Scenario
A teammate builds a `customers` table where the `phone_numbers` column stores `"555-1234, 555-5678"` as a comma-separated string, because "customers can have more than one phone number."

## Diagram
```
Violates 1NF:                          Satisfies 1NF:
+----+--------+------------------+     +----+--------+              +----+-------------+
| id | name   | phone_numbers    |     | id | name   |              | id | phone       |
+----+--------+------------------+     +----+--------+              +----+-------------+
| 1  | Alice  | 555-1234,555-5678|     | 1  | Alice  |              | 1  | 555-1234    |
+----+--------+------------------+     +----+--------+              | 1  | 555-5678    |
                                                                     +----+-------------+
```

## Problem
Explain why the comma-separated column violates 1NF, and what breaks in practice because of it.

## Solution
1NF requires every column to hold a single, atomic value - no repeating groups or multi-valued fields. `"555-1234, 555-5678"` packs two logical values into one cell.

Practical breakage: `WHERE phone_numbers = '555-5678'` fails to match (wrong string), you can't index individual numbers efficiently, adding a third number means string surgery in application code, and `COUNT(DISTINCT phone_numbers)` doesn't tell you how many unique phone numbers exist.

**Fix:** separate `CustomerPhone(customer_id, phone)` table, one row per phone number, or in a database that supports it, a native array column - though a separate table is usually still better for indexing and querying.

## Takeaway
If you ever find yourself splitting a column's value in application code with `.split(',')`, that column is very likely violating 1NF.
